# BRMARL v2

Синхронное обучение: **4 CPU-работника / 12 рынков / один процесс-владелец GPU**.
Распакуйте v2 в отдельный каталог и перезапустите старый kernel перед импортом пакета.
Два notebook, модули Python, отдельный frozen и online-тест, направленный маршрутный cache,
фиксированные progress bars и аудит времени. Исходные данные пользователя в архив не включены.

## Запуск

1. Установите `requirements.txt`. Для GPU установите CUDA-сборку PyTorch по инструкции https://pytorch.org/get-started/locally/.
2. Распакуйте весь проект. Выполняйте notebooks из каталога, содержащего пакет `brmarl/`.
3. Поместите `AUG_global_map_osrm_seconds.pkl`, `glob_pref_map.pkl`, существующий `distances.dat` в `data/`
   либо задайте `BRMARL_DATA_ROOT` и `BRMARL_DISTANCE_FILE`. Исходный набор: **385 полигонов, 13549 точек/столбцов заказов**.
4. Сначала выполните подготовку assets/cache в `01_train_brmarl.ipynb`, затем обучение и `02_test_brmarl.ipynb`.

По умолчанию MODE=original. Синтетическая инженерная карта включается только явно через
`BRMARL_MODE=fixture`; она не подставляется при отсутствии исходных данных или отказе OSRM.
`device='auto'` выбирает CUDA при её доступности, иначе CPU; явный `device='cuda'` без CUDA вызывает ошибку.
Все CUDA-параметры принадлежат одному родительскому процессу. GPU warm-up реализован; CUDA Graph capture не реализован.
Доступный здесь CPU-прогон не является подтверждением ускорения на вашей видеокарте.

## Исходные ID и memmap

В notebook можно передать уже созданные `distance_array` (именно np.memmap) и `idx_dict`, без копирования массива.
Индекс содержит абсолютные диапазоны строк для исходного from ID. Поиск to ID — searchsorted внутри диапазона.
Значения — секунды, направленные a→b; sentinel означает отсутствие и вызывает fallback, в расчёт не попадает.
Межполигональные штрафы отсутствуют. Метры не выводятся из секунд: distance_m в таких логах пустой.

Для связи координат с оригинальными ID экспортируйте assets заново:

```python
from brmarl.data import export_assets
export_assets(AUG_global_map, preferences_map, 'data/brmarl_assets.json', MPID_pl)
```

`point_ids` берутся из исходного `full map`. Если normalized assets созданы v1 и не имеют ID,
передайте `coordinate_to_id={(lat,lon):original_id,...}` в подготовку cache либо переэкспортируйте данные.
Новые центроиды не получают выдуманных оригинальных ID. Для них используется отдельный cache по координатам.
При изменении состава/порядка точек или профиля маршрутизации нужен другой каталог cache.

## Два направленных centroid-cache

`data.prepare_route_cache` вызывается **до spawn** и создаёт:

- `centroid_to_order.npy`: forward[c,o] = centroid[c]→order[o];
- `order_to_centroid.npy`: reverse[c,o] = order[o]→centroid[c].

Оба массива имеют форму `[n_centroids,n_order_columns]`. Reverse не является транспонированием forward.
При 385×20160 float32 это около 31 МБ на массив, 62 МБ на оба без метаданных. Дубликаты точек в исходных
облаках сохраняются как отдельные столбцы; координатный lookup использует эквивалентный столбец.

По умолчанию файлы выделены и заполнены NaN для неизвестных пар. **Это не предрасчёт всех 7.76 млн маршрутов.**
Для выбранного пула используйте `prewarm_centroid_pool(ROUTE_SPEC, centroid_indices, order_indices, reverse=True)`.
Там OSRM Table применяется только к явно запрошенному пулу, с ограниченными блоками. Полный prewarm может занять
значительное время и является отдельной фазой с собственным progress bar. На большой карте используйте свой OSRM.

Во время смены: legacy memmap → centroid memmap → общий delta-cache SQLite WAL → OSRM при промахе.
Работники читают centroid maps read-only. Серверные промахи защищены общим lock с повторной проверкой cache,
чтобы процессы не дублировали один запрос. Родитель после барьера сливает добавления в memmap и JSONL.
SQLite сохраняет найденные значения сразу, даже если пакет был прерван. JSONL-экспорт имеет watermark.

Для стоимостной оценки заказа десятью курьерами выполняются 21 скалярный запрос: 10 подач + 1 доставка + 10 возвратов.
Повторные обращения при регистрации обязательства читают cache. Декартовы матрицы в цикле рынка удалены.

## Исполнение и теневые ветки

Выигрыш создаёт безусловное обязательство. До окончания курьер недоступен для реальных заявок.
Его position остаётся **точкой отправления** — последним завершённым заказом или точкой после перерыва.
После исполнения она меняется на клиентскую точку, после завершения дрейфа — на новую точку.
Физическое положение внутри дорожного маршрута не вычисляется.

Busy-shadow использует этот departure anchor. Это локальная гипотеза пропуска текущего обязательства;
она не является точной альтернативной сменой и не превращает занятого курьера в допустимого участника.
Эти shadows остаются диагностическими и не учат верхнюю политику допустимого участия.

В `positions` сохранены anchors, не дорожные позиции. В maps/GeoJSON соединяются конечные точки;
поле `geometry_kind=endpoint_schematic` явно отличает их от реальных OSRM-полилиний.
Неизвестный случайный дрейф требует нового lookup/OSRM и snapping. После него найденные пары также кэшируются.
Остальная экономика v1 сохранена: B=43200, MARKET_HOUR_PRICE=500, максимум300 новых заказов, retries отдельно,
4800 секунд предела доставки, 1200–1800 только оценка, фактическое исполнение — сумма двух времён маршрута.
При отсутствии откликов U повышается до cap1800 с задержкой120с и максимумом20 попыток.
Перерыв N(900,300²), усечённый [600,1200], с sigmoid(h−B/4); homes фиксированы между сменами.

## Синхронное обучение

Число пакетов задаётся `n_batches`, не прежним `n_shifts`. Один пакет = 12 полных смен.
По умолчанию 20 пакетов дают до72000 новых заказов, но лишь20 actor-обновлений на курьера. Это бюджет,
а не гарантия достаточного обучения. `resume=.../checkpoint.pt` добавляет новые пакеты к сохранённой популяции.
Checkpoint атомарно сохраняется после каждого успешно завершённого пакета.

Внутри каждого CPU-процесса несколько event-loop потоков обслуживают рынки и ждут inference RPC.
Число Python-работников равно4; процессы не привязаны автоматически к конкретным P/E ядрам.
Только родитель собирает готовые наблюдения и делает tensor batches по идентичности агента.
Между рынками используются одни веса агента i; веса разных курьеров не объединяются.
Фактический microbatch зависит от готовности рынков, может быть меньше12 и записывается в статистике.
Внутренние CPU-потоки Torch ограничены одним на процесс. Отдельные модели, GRU/latent state и RNG
сохраняются для соответствующих ролей и реплик; голоса разных рынков не раскрываются агенту во время смены.

До завершения последней смены фиксированы **все neural weights, CFR и OSR prototypes**.
AL, preference belief и threshold memory локально обновляются по доступным исходам как состояние реплики.
После барьера данные объединяются в порядке market ID, адаптер получает один полный policy-gradient update
на агента; train_chunk делит его для памяти, но не создаёт промежуточных optimizer steps.
Следом обучается контекст и обновляются CFR/OSR.
Исправлено усреднение ценового CFR из v1: накапливаются текущие regret-matching политики,
а не прежние распределения BRMARL, иначе библиотека могла не использовать выученные regrets. Behavior log-probability проверяется до optimizer step.
Модельный advantage по умолчанию отключён (model_adv_weight=0), прежний смещённый вариант остаётся опцией.

Обновление акторов не повторяется многократно по старым данным: барьер сам по себе не делает повторные
actor-epochs on-policy. AL — эмпирический ориентир, не доказанное равновесное значение. EDL работает только
в неизвестной ветке. OSR bins/пороги и конечносеточный CFR остаются аппроксимациями первой версии,
не обещают Nash-сходимости и нуждаются в отдельных научных проверках.

## Тестовые протоколы

`02_test_brmarl.ipynb` отдельно запускает:

- frozen holdout: без обновления параметров и статистических beliefs;
- prequential online-тест: новый запуск из того же checkpoint, BRMARL учится внутри смены,
  предобученные GRU/OSR/CFR фиксированы в течение неё и обновляются между сменами.

Начальные seed совпадают, эндогенные траектории после разных действий могут расходиться.
Полные предложения/учебные counterfactual utilities раскрываются только после ставок. Oracle theta нет в features.
Коммерческий проигрыш даёт ноль; legacy unconditional payoff не смешивается с этим рынком.

## Прогресс и профилирование

12 bars создаются и обновляются **только родителем**, занимают фиксированные slots и переиспользуются между пакетами.
В Jupyter нужны ipywidgets и tqdm.notebook; в терминале — поддержка перемещения курсора.
В stdout-файл bars не рисуются. Они показывают модельные часы, фазу OSRM-ожидания, ожидание последней смены и learning.
Работники не печатают собственные строки. Бар по B не включает время возврата домой после B — оно отмечается фазой.

По каждой смене: tenders, decisions, awards, ledger, movements, positions, choice_updates (CSV+JSONL),
metrics.json, checks.json, timings.json, routing_stats.json, worker_timing.json и experience.pkl.
`routing_errors_*.jsonl` в каталоге cache записываются сразу при ошибке/timeout, не только в конце часа ожидания.

По пакету: `batch_timing.json`, политика/версия, simulation/barrier wall time, ожидание отставшей смены,
merge/learning/cache merge/checkpoint time, размер inference microbatches и обучающих наборов,
max_behavior_logprob_error. Timings с суффиксом inclusive вложены друг в друга: их нельзя суммировать.
RPC-wait включает очередь и вычисление, а не является чистым CUDA kernel time. GPU wall time имеет
синхронизацию на границе update; детальный CUDA-event profiler в эту версию не включён.

SHAP объясняет только end-of-shift BRMARL pricing head при фиксированных исторических context/latent/memory.
Его scope/selection сохранены; это не объяснение исторических весов, CFR gate или причинный эффект.
Отказы при initial_U учитываются отдельно от busy, выбора другого заказа и полной ценовой неосуществимости.
Они сами по себе не доказывают непрямого сговора.
